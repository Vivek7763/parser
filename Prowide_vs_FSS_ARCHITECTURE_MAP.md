# ISO 20022 Parser/Validator Architecture Map (Prowide vs FSS)

This document maps exactly what functionality is provided by Prowide versus what was custom-built by FSS. All statements and architectural paths are derived strictly from the current codebase.

## PART 3 — OUR PARSER
==================================================

- **`ISOParser`**: (`com.prowidesoftware.swift.model.mx.validation.ISOParser`)
  - Responsibility: Orchestrator. Directs the workflow from identification -> XSD validation -> Prowide parsing.
  - Why: To create a single entry point for validation and parsing without coupling them to semantic rules.
  - Prowide dependency: **NO direct dependency**. It relies on `ProwideAdapter` to shield itself from Prowide internals.

- **`ISOMessageIdentifier`**: (`com.prowidesoftware.swift.model.mx.validation.ISOMessageIdentifier`)
  - Responsibility: Strongly typed identifier containing business area, function, variant, version.
  - Why: Decouples FSS components (like `SchemaRegistry`) from Prowide's `MxId` class.
  - Prowide dependency: **NO**.

- **`ProwideAdapter`**: (`com.prowidesoftware.swift.model.mx.validation.ProwideAdapter`)
  - Responsibility: Acts as an anti-corruption layer isolating Prowide calls.
  - Why: So FSS logic does not tightly couple to Prowide's `MxParseUtils` or `AbstractMX`.
  - Prowide dependency: **YES** (`MxParseUtils.identifyMessage(xml)`, `AbstractMX.parse(xml)`).

- **`ISOParserResult`**: (`com.prowidesoftware.swift.model.mx.validation.ISOParserResult`)
  - Responsibility: DTO holding the results of the structural validation and parsing phases.
  - Why: Explicit separation of schema validation statuses from model parsing statuses.
  - Prowide dependency: **YES** (holds an instance of `AbstractMX`).

- **`MessageStructureInfo`**: (`com.prowidesoftware.swift.model.mx.validation.MessageStructureInfo`)
  - Responsibility: DTO containing details on exactly where the `AppHdr` and `Document` namespaces occur.
  - Why: Aids in extracting correct structural information during validation.
  - Prowide dependency: **NO**.

**Trace:** RAW XML → `ProwideAdapter.identifyMessage(xml)` → `ISOMessageIdentifier` → `SchemaRegistry.getSchema(identifier)` → `ISOValidator.validate(xml, schema)` → `ProwideAdapter.parseToModel(xml)` → `ISOParserResult`.

## PART 5 — XSD / STRUCTURAL VALIDATION
==================================================

- **`SchemaRegistry`**: Uses `ClasspathResourceResolver` to locate schemas inside `/schemas/`. Loads and caches `javax.xml.validation.Schema`.
- **`ISOValidator`**: Wraps the XML in a `SAXSource` using a custom `XMLFilter` to isolate the payload node, and runs `schema.newValidator().validate(source)`. Uses a custom `ErrorHandler`.
- **`ValidationResult`** & **`ValidationError`**: Maps `SAXParseException`s into a list of structured `ValidationError` records.
- **`SafeXmlUtils`**: (If present) Configures the `SAXParserFactory` to disable external DTDs and entities to prevent XXE.

**Flow:**
`ISOMessageIdentifier` → `SchemaRegistry.getSchema()` (Resolves via `ClasspathResourceResolver`) → `ISOValidator.validate(xml, schema)` → Builds `XMLReader` (securely configured) → validates via SAX → Intercepts `SAXParseException` → Converts to `ValidationResult(errors)`.

**Why not let Prowide parse first?**
Because Prowide's JAXB models do not preserve all XSD constraints (e.g., `maxLength`, `pattern`, precise numeric facets, specific `minOccurs`/`maxOccurs`). Prowide's `AbstractMX.parse` silently truncates or fails ungracefully if structural constraints are violated. Our standalone SAX XSD validation layer catches exact violations and reports their line/column before JAXB ever sees the data.

==================================================
## PART 6 — SECURITY HARDENING
==================================================

- **XXE Prevention & SAX Hardening**: Inside `ISOValidator` (and via custom `XMLReader`), features like `http://apache.org/xml/features/disallow-doctype-decl`, `http://xml.org/sax/features/external-general-entities`, and `http://xml.org/sax/features/external-parameter-entities` are disabled.
- **Schema Extensibility**: `SchemaRegistry` utilizes an explicit, localized `schemas/` directory to prevent fetching external DTDs or imports over HTTP.
- **Semantic SpEL Sandbox**: `SpELRuleEvaluator` builds a highly restricted context: `SimpleEvaluationContext.forReadOnlyDataBinding().withTypeConverter(...).build()`. This explicitly denies Java class instantiation, reflection, and method executions (`T(java.lang.Runtime)`). `SpELRuleHelpers` securely wraps operations like `sum()` so malicious strings are blocked.

==================================================
## PART 7 — SEMANTIC VALIDATION
==================================================

- **`SemanticRuleEngine`**: Central registry for rules; evaluates an `AbstractMX` against all loaded `SemanticRuleDefinition`s.
- **`SemanticRuleLoader`**: Loads semantic rules from JSON or resource files.
- **`SpELRuleEvaluator`**: The implementation of `RuleEvaluator` that uses Spring Expression Language (SpEL) in a locked-down sandbox.
- **`RuleContext`**: Contains state information (like profiles: "strict", "lenient") that dictates which rules are applicable.
- **`SemanticValidationResult`**: The final output collecting all `SemanticViolation`s and `TechnicalEvaluationError`s.

**Flow:**
`AbstractMX` (Prowide Model) → `SemanticRuleEngine.validate(model, context)` → Filters rules by `RuleContext` profiles → `SpELRuleEvaluator.evaluate(rule, model)` → SpEL executes against `AbstractMX` properties → `SemanticValidationResult` returned.

**Real Rule Example (`CHK-01` from tests):**
```java
rule.setExpression("#parseInt('10') == 10 && #getCurrencyDecimals('USD') == 2");
```
In real rules, SpEL accesses Prowide model properties directly, e.g., `FIToFIPmtStsRpt.GrpHdr.MsgId`. The engine relies heavily on Prowide's JAXB structure as the data graph for semantic evaluation.

## PART 8 — JSON
==================================================

**A. ISO Java model → JSON (Prowide JSON):**
Prowide uses `Gson` internally (`AbstractMX.toJson()`). We **DO NOT** use this functionality.

**B. FSS validation result → JSON (FSS ValidationResponse JSON):**
- **`ValidationResponse`**: The main DTO.
- **`ValidationResponseBuilder`**: Merges `ISOParserResult` and `SemanticValidationResult` into a `ValidationResponse`.
- **`FssError`**, **`ResponseStatus`**, **`ErrorCategory`**: Structured enums/classes used in the response.

We construct `ValidationResponse` as a standard Java POJO. Any translation to JSON happens external to this core module (e.g., via Jackson in a Spring REST controller). There is a distinct separation between Prowide's raw message JSON serialization and FSS's validation outcome JSON payload.

## PART 11 — COMPLETE END-TO-END TRACE
==================================================

**Trace for `pacs.002.001.12`:**

1. **XML String** → `ISOParser.parse(xml)` (FSS)
2. `ISOParser` → `ProwideAdapter.identifyMessage(xml)` (FSS)
3. `ProwideAdapter` → `MxParseUtils.identifyMessage(xml)` (Prowide)
4. `ProwideAdapter` returns `ISOMessageIdentifier` (FSS)
5. `ISOParser` → `SchemaRegistry.getSchema(identifier)` (FSS)
6. `ISOParser` → `ISOValidator.validate(xml, schema)` (FSS)
7. `ISOParser` → `ProwideAdapter.parseToModel(xml)` (FSS)
8. `ProwideAdapter` → `AbstractMX.parse(xml)` (Prowide)
9. `AbstractMX` returns `MxPacs00200112` (Prowide)
10. `ISOParser` returns `ISOParserResult` (FSS) containing the `MxPacs00200112` model.
11. **Caller (e.g. REST Controller)** → `SemanticRuleEngine.validate(MxPacs00200112, context)` (FSS)
12. `SemanticRuleEngine` → `SpELRuleEvaluator.evaluate(rule, MxPacs00200112)` (FSS)
13. `SemanticRuleEngine` returns `SemanticValidationResult` (FSS)
14. **Caller** → `ValidationResponseBuilder.build(ISOParserResult, SemanticValidationResult)` (FSS)
15. Returns final `ValidationResponse` (FSS).

## PART 14 — IMPORTANT: OLD VS CURRENT
==================================================

- **OLD CLAIM**: `ISOParser` orchestrates semantic validation and returns a unified result.
- **CURRENT CODE**: `ISOParser` *strictly* handles structure + JAXB model loading. `SemanticRuleEngine` is invoked *independently* by the caller, using the model provided by `ISOParserResult`.
- **ACTUAL STATUS**: Decoupled. `ISOParser` does NOT directly invoke `SemanticRuleEngine`. `ISOParserResult` no longer contains semantic statuses or rule counts.
